# Разработка

## Быстрый старт

```bash
# firmware
cd firmware
pio run -e esp32dev                 # сборка
pio run -e esp32dev -t upload       # прошивка
pio run -e esp32dev -t uploadfs     # заливка LittleFS (SPA + конфиги)
pio device monitor                  # 115200, с декодером стектрейсов

# тесты на хосте — железо не нужно
pio test -e native
tools/run_tests.sh                  # то же самое одним компилятором, без реестра
SAN=1 tools/run_tests.sh            # они же под ASan + UBSan

# шесть ESP32-файлов: парсятся ли и согласны ли с PsychicHttp / ArduinoJson
tools/esp32_typecheck/check.sh

# во что обходится каждый предел из core/Types.h
g++ -std=c++17 -O2 -I firmware/src -I /tmp/aj/src tools/ram_report.cpp <исходники> -o /tmp/ram

# frontend
cd ../frontend
npm ci
npm run dev                         # Vite, /api и /ws проксируются на плату
```

`pio run` автоматически собирает frontend (хук `tools/build_frontend.py`) и кладёт
gzip-нутые файлы в `firmware/data/www`. Отключается через `LC_SKIP_FRONTEND=1`.

Хук сам ставит зависимости, если `node_modules` нет, и **роняет сборку**, если
интерфейса нет, а цель — `uploadfs` или `buildfs`: залить пустой образ хуже, чем
не залить (ADR-0021). Для `pio run` без Node сборка прошивки по-прежнему
проходит — это осмысленно для CI и бессмысленно для заливки.

### Что можно проверить без платы, а что нельзя

| Проверка | Команда | Что доказывает |
|---|---|---|
| Шесть наборов тестов | `tools/run_tests.sh` | поведение всего, что не трогает Arduino |
| Санитайзеры | `SAN=1 tools/run_tests.sh` | память и UB на тех же тестах |
| Синтаксис ESP32-файлов | `tools/esp32_typecheck/check.sh` | скобки, типы и согласие с настоящими библиотеками |
| Бюджет статической RAM | `tools/run_tests.sh` (в `test_core`) | что ёмкости из `core/Types.h` влезают |
| Интерфейс против настоящего API | `tools/host_server` + `screenshot.mjs` | что UI и прошивка договариваются |
| **Влезает ли прошивка, работает ли периферия** | `pio run`, плата | **только плата** |

Первые пять — секунды и не требуют тулчейна. Последняя строка — причина, по
которой Milestone 12 существует: одиннадцать этапов проверяли первые пять и
считали, что этого достаточно.

## Три окружения

| env | Назначение |
|---|---|
| `esp32dev` | основная плата, ESP32 DevKit / WROOM-32 |
| `esp32s3` | проверка переносимости, PSRAM |
| `native` | **ядро и services на хост-компиляторе**, unit-тесты |

Окружение `native` — не формальность. Оно заставляет `core/` и `services/` не
зависеть от Arduino, и как побочный эффект даёт тесты планировщика, менеджера
ресурсов, каналов и калибровки, которые проходят за миллисекунды и не требуют платы.
Если новый файл в `core/` не собирается в `native` — это ошибка проектирования,
а не проблема сборки.

## Правила зависимостей

```
core      → ничего (только STL и <cstdint>)
services  → core                       ← не знает ни про JSON, ни про файлы
buses     → core                       ← интерфейсы; buses/esp32 → Arduino
modules   → core, services, buses      ← только интерфейсы шин, не реализации
storage   → core, services, platform, ArduinoJson
app       → core, services, storage    ← единственный, кто знает и то и другое
api       → core, services, storage, app   ← api/esp32 дополнительно → PsychicHttp
platform  → Arduino / ESP-IDF
main.cpp  → app                        ← и только композиция
```

Обратные зависимости запрещены. `core` не знает про `services`, `services` не знает
ни про `storage`, ни про `api`. Правило проверяется тем, что окружение `native`
собирает `core` + `services` + `storage` + `app` без Arduino вообще; попытка
подключить `Arduino.h` из `core/` или `services/` ломает сборку тестов.

## Соглашения по коду

* C++17, исключения и RTTI выключены. Ошибки — `Status` / `Result<T>`.
* Именование: `PascalCase` типы, `camelCase` методы и переменные,
  `member_` с подчёркиванием в конце, `kConstant`, `g_` только для объектов
  композиционного корня в `main.cpp`.
* **Никаких** `String`, `std::string`, `new`/`malloc` в горячем пути. Аллокации
  разрешены только в фазе применения конфигурации.
* Никаких `std::function` там, где вызывается чаще ~100 раз в секунду:
  указатель на функцию + `void* context`.
* Все контейнеры ядра — фиксированной ёмкости, лимиты в `core/Types.h::limits`.
  Увеличение лимита — осознанное изменение с известной ценой в RAM.
* `delay()` не используется как механизм планирования. Единственное исключение —
  200 мс в `setup()` на перечисление USB-CDC.
* Комментарий объясняет **почему**, а не что. «Increment counter» не нужен;
  «ADC2 не работает при активном Wi-Fi, поэтому запрещаем» — нужен.
* Каждая нетривиальная ошибка получает `ErrorCode` и внятный `detail`.
  Немых ошибок нет (§46).

## Тесты

```
firmware/test/
├── test_core/       FixedString, EventBus, Scheduler, ResourceManager, ModuleRegistry
├── test_services/   ChannelManager, CalibrationSolver, процессоры, SignalSimulator
├── test_devices/    DeviceManager (валидация, откат, жизненный цикл), ProcessingManager
├── test_storage/    ConfigStorage, миграции, атомарность, SystemManager, критерий M1
└── test_modules/    драйверы на фальшивых шинах: AHT20, BMP280, HX711, входы, сканер
```

Состояние на конец Milestone 16: **209 тестов прошивки + 18 тестов раскладки + 28 тестов
истории графиков + 26 тестов локального архива + 23 теста выгрузки сегментов +
6 тестов домашней сети**, сборка без
предупреждений при `-Wall -Wextra -Wshadow`, чисто под AddressSanitizer и UBSan.

Два теста прошивки падают **до** M13 и не относятся к нему — их уронило
добавление новых сенсоров, а не изменения графика:

| Тест | Что говорит | Причина |
|---|---|---|
| `test_module_registry_rejects_duplicates` | ожидал 6 модулей, найдено 11 | в реестр добавлены новые модули, число в тесте не обновлено |
| `test_bmp280_identifies_the_chip_before_trusting_it` | ожидал «this is a BME280, not a BMP280», получил «implausible calibration data» | проверка chip id перекрыта более ранней проверкой калибровочных данных |

Оба падения воспроизводятся на коммите до M13 и к M14/M15 отношения не имеют.
К пяти каталогам выше добавился `test_api/` — маршрутизация, конверт ошибки,
`?dry_run=1`, отчёт о загрузке, батчинг телеметрии, калибровка сквозь REST.

`test_devices` использует специально написанный фальшивый драйвер, а не реальный
датчик: смысл этих тестов — проверить валидацию, откат ресурсов и жизненный цикл,
а фальшивый драйвер можно заставить упасть ровно там, где нужно, чего от BMP280
не добиться.

Что тестируется в первую очередь (§58): парсер формул, калибровка, ResourceManager,
правила, PID, парсер конфигурации — то есть всё, где ошибка даёт не падение,
а тихо неверное число.

Аппаратные проверки: у каждого драйвера есть `selfTest()`, доступный со страницы
диагностики. Это не замена unit-тестам, а способ за десять секунд ответить на
вопрос «датчик вообще подключён правильно?».

## Проверка интерфейса

```bash
cd frontend && npm ci && npm run check && npm test && npm run build   # типы + раскладка + бандл
make -C tools host-server                                  # прошивка на PC
./tools/host_server 8080 /tmp/lc-host frontend/dist
node tools/screenshot.mjs                                  # сценарий приёмки
```

`tools/screenshot.mjs` проходит через Playwright полный путь всех этапов:
каталог модулей → выбор HX711 → ошибка валидации от настоящего
`ResourceManager` → исправление → создание → калибровка по трём гирям →
редактор конвейера → сборка дашборда, перетаскивание виджета и **проверка, что
раскладка пережила перезагрузку страницы** (сценарий падает, если нет). Скриншоты складываются в указанную папку.
Сценарий сам удаляет устройства, созданные предыдущим прогоном: конфигурация
host-сервера лежит на диске, а занятый ключ теперь честно отвергается и на
`?dry_run=1`. С Milestone 12 он ещё и **создаёт стенд**, на который ссылается:
каналы `t_bath` и `heater` приходили из устройств, заведённых руками когда-то
раньше, и на чистом каталоге прогон падал по таймауту, ничего не говорящему о
причине.

## Порядок работы над этапом

Для каждого milestone: сформулировать задачу → предложить архитектуру → зафиксировать
интерфейсы → показать структуру файлов → реализовать → объяснить интеграцию →
написать тесты → проверить граничные случаи → обновить документацию → описать
следующий шаг.

Существенное архитектурное изменение оформляется по §55: проблема → текущее решение →
предлагаемое → плюсы → минусы → стоимость миграции. Принятое решение фиксируется ADR
в `docs/adr/` (Context / Decision / Alternatives / Consequences).

## M15.2 — перезагрузка каждые 43 секунды (`0.15.2-m15`)

После M15.1 сеть и HTTP поднимаются штатно, но плата стала уходить в
перезагрузку примерно через 43 секунды после старта — и так по кругу:

```text
[psychic] Server started on port 80
http: listening on port 80
...
Backtrace: 0xfffffffe:0x8008e498 |<-CORRUPTED
Rebooting...
```

Постоянство интервала (43,2 с и 43,0 с в двух циклах) — признак накопления
ресурса с фиксированной скоростью, а не случайного сбоя. Строки
`[LOGGING_STARTED]` перед падением нет, то есть логирование не при чём: авария
происходит до него. Это **другая** неисправность, чем в M15.1.

### Причина: телеметрия WebSocket копится в куче

Мой собственный комментарий в `PsychicHttpAdapter::canSend()` утверждал, что
`esp_http_server` отправляет синхронно из задачи HTTP и очереди кадров не
существует. **Это было неверно.** В `PsychicWebSocket.cpp` каждый кадр:

```cpp
httpd_ws_frame_t* ws_pkt = (httpd_ws_frame_t*)malloc(sizeof(httpd_ws_frame_t));
ws_pkt->payload = (uint8_t*)malloc(len);      // копия полезной нагрузки
memcpy(ws_pkt->payload, data, len);
httpd_ws_send_data_async(server(), socket(), ws_pkt, _sendMessageCallback, ws_pkt);
```

Память освобождает callback, который срабатывает **только когда кадр
действительно ушёл**. Клиент, переставший разбирать сокет (планшет вышел из
зоны, ноутбук уснул, полуоткрытое TCP-соединение), не замедляет телеметрию — он
заставляет её накапливаться. Двенадцать каналов на 5 Гц — это пять аллокаций в
секунду, которые никогда не освобождаются. Исчерпание кучи при постоянной
скорости выделения — это часы, отсюда и повторяемые 43 секунды.

В 2.2.0 ограничения нет. В 3.1.2 появился счётчик кадров «в полёте» на клиента
(`PSYCHIC_WS_MAX_PENDING_FRAMES`, по умолчанию 8): при заполнении очереди кадр
отбрасывается. Для телеметрии это правильное поведение — живому графику нужно
последнее значение, а не очередь устаревших.

### Две независимые защиты

Одной внешней библиотеки мало, поэтому защит две:

1. `PSYCHIC_WS_MAX_PENDING_FRAMES=4` в `platformio.ini` — ограничение внутри
   библиотеки, на каждого клиента.
2. Порог по куче в `canSend()` — **не зависит** ни от версии библиотеки, ни от
   значения макроса, ни от числа клиентов. Ниже 40 КБ свободной кучи или 4 КБ
   наибольшего непрерывного блока телеметрия молча приостанавливается и так же
   молча возобновляется, когда клиент разберёт очередь.

Отбрасывать кадры телеметрии — правильный отказ, и это стоит сказать прямо:
ничего незаменимого этим путём не идёт. Наборы данных пишутся через `LogStore`,
сегменты передаются с контрольной суммой и подтверждением. `TelemetryBatcher`
при отказе сохраняет отметки «грязных» каналов, так что следующий кадр несёт
более свежие значения — потерянного нет, есть пропущенные промежуточные.

Счётчик отброшенных кадров виден на странице диагностики.

### Обновление PsychicHttp 2.2.0 → 3.1.2

Мажорное обновление HTTP-библиотеки затрагивает все маршруты, а не только
телеметрию, поэтому проверено отдельно. 3.1.2 **меняет API**
`PsychicFileResponse`: появился `psychic::FS`, а конструктор от `fs::FS&` ушёл
под `#ifdef ARDUINO`. Наш вызов продолжает собираться, потому что реальная
сборка определяет `ARDUINO`, а `psychic::FS(fs::FS&)` объявлен `explicit` —
неоднозначности при разрешении перегрузки нет.

`tools/esp32_typecheck/check.sh` теперь определяет `ARDUINO` (без него
библиотека выбирает ветку нативного ESP-IDF и сообщает о поломке, которой на
плате не существует) и умеет проверять **вторую** версию:

```bash
PSYCHIC_ALT_SRC=/path/to/psychic-2.2.0/src tools/esp32_typecheck/check.sh
```

Обе версии собираются. Это делает откат на 2.2.0 однострочным и проверенным —
если 3.1.2 поведёт себя на стенде плохо, возвращаться будет к чему.

### Порог безопасной загрузки

`SystemManager::kHealthyUptimeUs` был равен 30 секундам, а падение происходило
на 43-й. Каждый цикл обнулял счётчик неудачных загрузок за 13 секунд до аварии,
поэтому три подряд не накапливались **никогда** и режим `SAFE` не включался.
Порог поднят до 120 секунд: он должен переживать самую медленную правдоподобную
аварию, а не самую быструю.

Тест `test_a_crash_after_the_healthy_mark_still_reaches_safe_mode` роняет стенд
на 43-й секунде трижды и требует безопасного режима. На пороге 30 с он падает.

### Найдено, но не исправлено: гонка со списком клиентов

`PsychicWebSocketHandler::sendAll()` перебирает `std::list<PsychicClient*>`,
который задача HTTP изменяет при каждом подключении и отключении браузера.
Ничто эти две задачи не синхронизирует. Перебор списка, из которого другая
задача вырезает узлы, — неопределённое поведение с той же сигнатурой
`|<-CORRUPTED`.

Проверено: в 3.1.2 гонка **остаётся** — добавленный там мьютекс защищает буфер
приёма, а не список клиентов.

Причиной 43-секундных перезагрузок это не является: та авария не требовала
переподключений, а её интервал слишком регулярен для гонки. Поэтому записано,
а не «исправлено наугад»: закрыть её — значит перенести отправку на задачу HTTP
через `httpd_queue_work`, а это изменение, которое не покрывает ни один
здешний тест и не подтверждает ни один стенд.

**Если перезагрузки останутся** и будут совпадать с открытием или перезагрузкой
страницы, а не с тем, что вкладка просто оставлена открытой, — начинать надо
отсюда. Комментарий с подробностями стоит над `clientCount()`.

### Что проверено и что нет

| Проверено | Как |
|---|---|
| Порог безопасной загрузки | новый тест падает на 30 с, проходит на 120 с |
| Сборка против 3.1.2 | `check.sh` с `ARDUINO`, все шесть ESP32-файлов |
| Откат на 2.2.0 возможен | `PSYCHIC_ALT_SRC=...` — тоже собирается |
| Отбрасывание кадров не теряет данные | существующий тест батчера: отметки сохраняются |
| Весь набор | 201 тест прошивки, 95 фронтенда, чисто под ASan/UBSan |

**Требует железа:** сам факт, что перезагрузки прекратились. Механизм аварии
подтверждён чтением исходников библиотеки, а не наблюдением на плате — здесь
нет ESP32. Критерии §10 задания (30 минут с открытым интерфейсом, два закрытых
сегмента, ограниченный расход кучи при остановившемся клиенте) проверяются
только на стенде.

Быстрая проверка причины **до** прошивки, из §8 задания: отключить все браузеры
от точки доступа и оставить контроллер на две минуты. Если без браузера
перезагрузок нет, а с открытым интерфейсом они возвращаются через ~43 секунды —
диагноз подтверждён.

## M15.1 — авария и отказ HTTP (`0.15.1-m15`)

Плата уходила в перезагрузку с нечитаемым backtrace, а после программного
сброса веб-интерфейс не поднимался:

```text
Backtrace: 0xfffffffe:0x8008e498 |<-CORRUPTED
...
[SYSTEM_MESSAGE] src=0 code=OK access point started (192.168.4.1)
[psychic] Server start failed - no network interface available.
```

Это две **независимые** неисправности. Вторая появляется после первой, но не
вызвана ею.

### Первопричина: переполнение стека при сборке строки CSV

`DataLogger::appendRow` складывал результаты `snprintf` без проверки:

```cpp
char row[512];
used += std::snprintf(row + used, sizeof(row) - used, ...);
```

`snprintf` возвращает длину, которая *потребовалась бы*, а не записанную. Одно
усечение уводит `used` за размер массива, после чего следующий вызов получает
`row + used` за границей и `sizeof(row) - used` — беззнаковую разность, которая
обернулась примерно в четыре миллиарда. Это разрешение писать куда угодно.

Достижимо на обычной установке: цикл по каналам выходил при `used < 464`, а один
столбец `,%.*f` для значения порядка `1e38` занимает свыше сорока символов, плюс
`,%.6g` для сырого. Шестнадцать каналов — и финальный `snprintf` маски качества
пишет за пределы стекового кадра, затирая адрес возврата. Отсюда и
`|<-CORRUPTED`: обработчик паники уже не может раскрутить стек.

M15 сделал это заметно достижимее: `,global_row` добавляет ~11 байт в каждую
строку.

Зафиксировано AddressSanitizer'ом на хосте — `stack-buffer-overflow, WRITE of
size 4` в `DataLogger.cpp:285`, буфер объявлен на строке 236.

**Исправлено:**

* `core/Format.h` — `appendFormat()`: `used` никогда не превышает ёмкость,
  усечение возвращается как `false`. Все накопительные `snprintf` в
  `DataLogger` и `LogStore` переведены на него.
* Буфер строки **выведен из пределов**, а не назначен: `kRowBytes` считается из
  `kMaxLoggedChannels` и худшей ширины столбца, и лежит в `.bss`, а не на стеке
  задачи (у которой под ним Wi-Fi и LittleFS).
* Точность столбца ограничена девятью знаками. Она приходит из JSON без верхней
  границы: `"precision": 200` — это столбец в 240 символов. У `float` около семи
  значащих цифр, так что больше девяти — шум с широким следом на стеке.
* Строка не помещается — она считается потерянной, а не пишется усечённой.
  Обрезанная строка посреди набора хуже видимого пропуска: пропуск для того и
  существуют `global_row` и `dropped_rows`.

### Тот же класс ошибки в заголовке сегмента

`LogStore::ensureSegmentHeader` собирал заголовок так же и передавал `used` в
`backend_.append()` как длину записи. При широкой строке столбцов файловая
система читала несколько сотен байт за буфером и клала их в набор данных, а
учёт байтов расходился с диском. Заголовок разделён: метаданные в буфере с
проверками, строка столбцов пишется **отдельным** append и никогда не проходит
через него. Список калибровок обрезается осознанно и сообщает `(+N more)`.

Регрессия: `test_the_header_never_writes_more_than_it_holds` сверяет, что
`bytes` в индексе равен реальному размеру файла.

### Одновременный доступ к `LogStore` из двух задач

Обработчик HTTP выполняется на собственной задаче FreeRTOS, флаш логгера — на
задаче `loop()`. Обе читали `/data/logs.json` целиком, правили и записывали
обратно. При наложении вторая запись молча отменяет правку первой: либо
подтверждённый и удалённый сегмент возвращается в очередь как файл, которого
нет, либо только что закрытый сегмент пропадает из индекса и становится
сиротой. `core/Lock.h` сериализует короткие операции с метаданными. Передача
самого CSV идёт вне `LogStore` и **не** держит замок — иначе медленный клиент
останавливал бы флаш и ронял строки.

### Гонка Wi-Fi → HTTP

`WiFi.softAP()` возвращается, как только запрос принят; `esp_netif` под ним
поднимается асинхронно. PsychicHttp перед стартом проверяет, что интерфейс
существует, поднят и имеет ненулевой адрес — и отказывается, пока это не так.
Холодный старт обычно проскакивал окно, `SW_CPU_RESET` — нет: всё уже прогрето,
и `setup()` доходит до HTTP раньше. Отсюда «точка доступа запущена» и «нет
сетевого интерфейса» подряд в одном журнале.

`WifiManager::interfaceReady()` задаёт те же три вопроса, что и библиотека,
`waitUntilReady()` ждёт их выполнения, а `loop()` повторяет запуск, если сеть
появилась позже. Фиксированная задержка была бы соблазнительным и неверным
решением — она работает на стенде и отказывает на загрузке, где инициализация
заняла чуть дольше, то есть ровно так, как эта ошибка себя и вела.

`PsychicHttpAdapter::begin()` разделён: маршруты регистрируются один раз,
повторяется только старт. До этого каждый повтор заново регистрировал бы
обработчики и тёк бы кучей — поэтому безопасной была ровно одна попытка, и
именно одна попытка оставляла прибор без веб-интерфейса.

### Что проверено и что нет

| Проверено | Как |
|---|---|
| Переполнение строки | ASan на хосте: падает до исправления, чисто после |
| Учёт байтов заголовка | `test_the_header_never_writes_more_than_it_holds` |
| Границы `appendFormat` | `test_append_format_never_walks_past_the_end` |
| Весь набор M15 | 199 тестов + сквозной сценарий Playwright, чисто под ASan/UBSan |
| Сборка ESP32-файлов | `tools/esp32_typecheck/check.sh`, включая `LC_MEM_DIAGNOSTICS=1` |

**Требует железа и здесь не выполнено:** десять последовательных `ESP.restart()`
с проверкой доступности HTTP (§13 задания) и 24-часовой прогон непрерывного
логирования с контролем `getMinFreeHeap()` (§14). Для этого предназначено
окружение `esp32dev-debug` — оно включает `LC_MEM_DIAGNOSTICS`, то есть отчёты о
куче и стеке и полную проверку целостности кучи вокруг ротации и ACK:

```bash
pio run -e esp32dev-debug -t upload
pio device monitor -e esp32dev-debug     # esp32_exception_decoder
```

ELF из `.pio/build/esp32dev-debug/` нужно сохранить от той самой сборки, что
дала панику: пересборка сдвигает адреса, и расшифровка становится вымыслом.

## Диагностика (§41)

Страница диагностики показывает: загрузку CPU, свободную и минимальную кучу,
фрагментацию, PSRAM, использование Flash и файловой системы, uptime, RSSI,
число HTTP- и WS-клиентов, задержку главного цикла, длительности и переполнения
задач планировщика поимённо, ошибки шин по устройствам, счётчики отброшенных
WS-кадров и подавленных отсчётов.

Это не украшение: почти все проблемы такого проекта — «через шесть часов упало» и
«иногда пропадают точки». Без этих счётчиков они не диагностируются.
