# Каналы, обработка и виртуальные каналы

## 1. Что такое канал

Канал — именованный поток чисел с единицей измерения, меткой времени и признаком
качества. Это единственная сущность, с которой работают дашборды, графики, PID,
правила, эксперименты и логгер.

```cpp
struct ChannelDescriptor {
  KeyString  key;                  // "mass_01"  — стабильный, на него ссылаются формулы
  NameString name;                 // "Sample mass"
  UnitString unit;                 // "g"
  FixedString<16> quantity;        // "mass" — физическая величина
  DeviceHandle    source;          // 0 = виртуальный канал
  ChannelDirection direction;      // input | output
  float minimum, maximum;          // диапазон достоверности
  std::uint8_t precision;
  std::uint32_t color;
  bool logged, visible;
  Micros expectedIntervalUs;       // для детекции «залипания»
  Geometry geometry;               // положение в установке
};

struct ChannelValue {
  float raw, calibrated, processed;
  Micros  timestampUs;             // монотонное время
  EpochMs epochMs;                 // настенное время; 0 если не синхронизировано
  std::uint32_t sequence;
  ChannelQuality quality;
};
```

### Зачем три значения

| Значение | Когда нужно |
|---|---|
| `raw` | пересчёт результатов эксперимента после уточнения калибровки; диагностика (датчик жив, но калибровка кривая); научная воспроизводимость (§48) |
| `calibrated` | физическая величина без сглаживания — на ней считаются производные и оценивается шум |
| `processed` | то, что видит оператор и что уходит в PID |

12 байт на канал. При 48 каналах это ~0.6 КБ — приемлемая цена за возможность
пересчитать вчерашний эксперимент, а не переделывать его.

### `quantity` — не косметика

Строка `quantity` (`temperature`, `mass`, `pressure`, `humidity`, `distance`,
`voltage`, `current`, `power`, `ratio`, `count`, `raw`) используется для:

* выбора виджета по умолчанию (температура → gauge со шкалой, масса → numeric);
* подсказки совместимых источников при настройке компенсации и PID;
* конвертации единиц в UI (°C ↔ K, g ↔ kg) без вмешательства в firmware.

## 2. Качество отсчёта

| Значение | Смысл |
|---|---|
| `UNKNOWN` | канал ещё ни разу не измерялся с момента старта |
| `GOOD` | свежий отсчёт в пределах диапазона, устройство здорово |
| `STALE` | нет новых данных дольше 3 ожидаемых периодов |
| `OUT_OF_RANGE` | вне `[minimum, maximum]` — значение **сохраняется**, а не отбрасывается |
| `SATURATED` | клиппинг АЦП/датчика |
| `FAULTED` | источник в `ERROR`, либо NaN/Inf |

Значение вне диапазона показывается, а не прячется: скрытая аномалия — это
скрытая неисправность. UI подсвечивает такой отсчёт, логгер пишет и значение, и флаг.

**Переход качества — это событие, а не побочный эффект отсчёта.** `STALE` и
`FAULTED` возникают именно тогда, когда отсчёты прекратились: устройство
отказало и его задача опроса выключена, или данные просто перестали приходить.
Поэтому `tick()` и `setSourceQuality()` уведомляют слушателей о самом переходе.
Иначе телеметрия, помечающая канал «грязным» из обработчика нового отсчёта,
никогда бы о нём не узнала, и браузер часами рисовал бы последнее число как
свежее — то есть поле качества существовало бы, но не работало.

## 2a. Калибровка (Milestone 5)

Калибровка — **неизменяемая запись с версией**, а не набор коэффициентов внутри
конвейера (ADR-0014). Перекалибровка добавляет версию; откат — активация версии,
которая никуда не девалась.

```
POST /api/v1/calibrations/solve   подгонка и остатки, НИЧЕГО не сохраняет
POST /api/v1/calibrations         + активация; создаёт mass_01#N
POST /api/v1/calibrations/{id}/activate | /deactivate
GET  /api/v1/calibrations?channel=mass_01   история версий
DELETE /api/v1/calibrations/{id}  отказ, пока запись активна
```

| Тип | Точек минимум | Когда |
|---|---|---|
| `offset` | 1 | тара: сдвиг без изменения наклона |
| `linear` | 2 | почти всё: тензодатчик, термопара, делитель |
| `poly2` | 3 | когда остатки линейной подгонки складываются в дугу |
| `poly3` | 4 | редко оправдан: четыре точки и кубика воспроизводят точки и больше ничего |
| `table` | 2 | кусочно-линейная; между точками интерполирует, снаружи **зажимает** |

Показывается не одно число, а три плюс остаток по каждой точке. R² = 0.9999
рядом с одной гирей, промахнувшейся на 0.4 г, — это не хорошая калибровка, и
именно среднее её прячет.

**Единица измерения двигается вместе с числом.** Активация калибровки переносит
на канал `unit`, `precision` и диапазон; снятие возвращает объявленные при
создании. Канал, показывающий сырые отсчёты под единицей «g», хуже, чем
некалиброванный: число выглядит правдоподобно и таковым не является.

Некалиброванный канал — это `calibrated == raw`, и страница каналов так и
пишет: «uncalibrated».

## 3. Конвейер обработки

```
raw ─► [0] Calibration ─► [1] Median ─► [2] Moving Average ─► [3] Compensation ─► processed
              │
              └── значение с этого шага записывается как `calibrated`
```

Порядок — это не оформление. Скользящее среднее по отсчётам АЦП, за которым
следует калибровка, и калибровка, за которой следует скользящее среднее, — это
разные числа, и разница не бросается в глаза.

### Библиотека процессоров (Milestone 5)

| Стейдж | Что делает | На что обратить внимание |
|---|---|---|
| `calibration` | сырое → физическое | управляется редактором калибровок, не этой формой |
| `moving_average` | boxcar, O(1) | пик выживает в среднем и размазывается по окну |
| `median` | отбрасывает выбросы | окно только нечётное; до заполнения отсчёт подавляется |
| `low_pass` | IIR с постоянной времени в секундах | коэффициент считается по **реальному** интервалу |
| `deadband` | подавляет мелкое движение | искажает сигнал намеренно: для логов, не для регулятора |
| `derivative` | скорость изменения за окно | до заполнения окна отсчёт подавляется, а не выдаётся нулём |
| `integral` | трапеции по времени | прямоугольники дали бы 55 вместо 50 на линейном разгоне |
| `statistics` | mean / min / max / размах / СКО | СКО в два прохода: однопроходная формула на 20 ± 0.01 даёт мусор |
| `clamp` | зажать или пометить недействительным | зажатие **скрывает** выход за диапазон от проверки канала |

Все — фиксированной ёмкости, без аллокаций после `configure()`. Не более
шести стейджей на канал (`limits::kMaxProcessorsPerChannel`).

* порядок задаёт пользователь и он хранится в `processing.json`;
* каждый шаг — `IProcessor`: один вход, один выход, состояние внутри;
* шаг может вернуть `valid = false` (медиана ещё не набрала окно) — тогда отсчёт
  подавляется целиком, `raw` при этом обновляется, счётчик `suppressedSamples` растёт;
* максимум `kMaxProcessorsPerChannel = 6` шагов — этого хватает с запасом, а лимит
  делает стоимость обработки предсказуемой.

`processing.json`:

```json
{
  "schemaVersion": 1,
  "pipelines": {
    "mass_01": {
      "calibration_stage": 0,
      "stages": [
        { "type": "calibration",    "config": { "type": "polynomial",
                                                "coefficients": [-500.0, 0.5],
                                                "x_center": 0, "x_scale": 1 } },
        { "type": "median",         "config": { "window": 5 } },
        { "type": "moving_average", "config": { "window": 16 } }
      ]
    }
  }
}
```

### Доступные процессоры

| type | Статус | Параметры |
|---|---|---|
| `calibration` | ✅ M0 | `type: identity\|polynomial\|table`, коэффициенты, таблица |
| `moving_average` | ✅ M0 | `window` (1…64) |
| `median` | M5 | `window` (нечётное, 3…15) |
| `lowpass` | M5 | `tau_s` — однополюсный IIR, шаг по фактическому dt |
| `derivative` | M5 | `window_s` — регрессия по окну, а не разность соседей |
| `integral` | M5 | `reset_on_start` |
| `statistics` | M5 | выдаёт min/max/σ как отдельные виртуальные каналы |
| `clamp` | M5 | `min`, `max` |
| `deadband` | M5 | `threshold` — подавляет дрожание последнего разряда |

## 4. Калибровка

Пользователь вводит эталонные точки; коэффициенты считает прошивка.

| Тип | Формула | Минимум точек |
|---|---|---|
| Offset | `y = x + b` | 1 |
| Linear | `y = a·u + b` | 2 |
| Polynomial | `y = Σ aᵢ·uⁱ`, i ≤ 4 | order + 1 |
| Table | кусочно-линейная интерполяция | 2 |

где `u = (x − x_center) / x_scale`.

**Почему обязательно `u`, а не `x`.** Подгонка полинома прямо на сырых счётчиках
HX711 (~5·10⁵) даёт в нормальных уравнениях числа порядка 10²⁴. В `float` результат —
мусор, в `double` — потеря половины значащих цифр. Поэтому `CalibrationSolver` всегда
центрирует и нормирует абсциссу и возвращает `x_center`/`x_scale` вместе с
коэффициентами. **Коэффициенты без своего преобразования бессмысленны** — храните
их только вместе.

Вместе с коэффициентами solver возвращает `rms_residual`, `max_residual`, `r_squared`.
UI обязан их показывать: калибровку, качество которой оператор не может оценить,
не стоит применять.

Пример из ТЗ (проверен тестом `test_linear_fit_of_load_cell_reference_points`):

| RAW | Reference |
|---:|---:|
| 453211 | 0 g |
| 498322 | 100 g |
| 543419 | 200 g |

→ `x_center = 498317.3`, `x_scale = 45104`, коэффициенты `[100.0, 100.0]`,
максимальная невязка 0.010 г, R² > 0.99999.

Таблица интерполируется **с обрезкой по краям**, а не экстраполируется: экстраполяция
lookup-таблицы — это как раз тот механизм, из-за которого тензодатчик с отвалившимся
проводом показывает правдоподобные 900 г.

### Версионирование калибровок

`calibrations.json` хранит историю: каждая запись — `{id, channel, created, operator,
points[], fit{}, active}`. Активна одна. CSV-лог эксперимента ссылается на `id`,
поэтому «какой калибровкой это померено» — вопрос с однозначным ответом даже через год.

## 5. Компенсация

Компенсация по другому каналу — это **виртуальный канал**, а не процессор:
у неё два входа, а `IProcessor` по контракту одновходовой.

```json
{ "key": "mass_corrected", "unit": "g", "quantity": "mass",
  "formula": "mass_01 + k * (temp_01 - t_ref)",
  "constants": { "k": -0.0032, "t_ref": 22.0 } }
```

Механизм не привязан ни к какому типу датчика — компенсировать можно что угодно чем угодно.

## 6. Виртуальные каналы и Formula Engine

```json
{ "schemaVersion": 1, "channels": [
  { "key": "delta_t", "name": "ΔT", "unit": "K", "quantity": "temperature",
    "formula": "t_center - t_edge", "rate_hz": 5 },
  { "key": "power", "unit": "W", "quantity": "power",
    "formula": "voltage_01 * current_01" },
  { "key": "evap_rate", "unit": "g/s", "quantity": "raw",
    "formula": "-d(mass_01)/dt", "window_s": 10 },
  { "key": "rel_change", "unit": "", "formula": "(x - x0) / x0",
    "constants": { "x0": 12.5 }, "inputs": { "x": "mass_01" } }
] }
```

Правила Formula Engine:

* **никакого выполнения произвольного C/C++** (§50). Выражение парсится в компактное
  дерево/RPN один раз при сохранении и потом только вычисляется;
* поддерживаются: `+ − * / ^`, скобки, унарный минус, сравнения, `and/or/not`,
  функции `abs, min, max, sqrt, exp, ln, log10, sin, cos, tan, atan2, clamp, if`;
  агрегаты по окну `mean, median, min, max, std, d/dt, integral`;
* операнды — ключи каналов и именованные константы; неизвестный идентификатор —
  ошибка `FORMULA_PARSE_ERROR` **при сохранении**, а не при первом вычислении;
* граф зависимостей проверяется на ацикличность (`FORMULA_CYCLE`) и пересчитывается
  в топологическом порядке;
* деление на ноль и NaN дают `quality = FAULTED`, а не тихий мусор;
* глубина выражения ограничена (16), чтобы стоимость вычисления была предсказуемой.

## 7. Частоты

Четыре независимые частоты (§16):

| Частота | Кто задаёт | Пример |
|---|---|---|
| Acquisition | `sample_interval_us` устройства, ограничен манифестом | HX711 80 Гц |
| Processing | равна acquisition (конвейер синхронный) | 80 Гц |
| Logging | `DataLogger`, децимация | 20 Гц |
| Dashboard | батчер WebSocket | 5 Гц |

Частота физического измерения **не связана** с частотой обновления браузера.
Закрытая вкладка не меняет ни данные эксперимента, ни работу PID.

## 8. Геометрия

```json
{ "system": "cylindrical", "a": 0, "b": 0, "c": 4,
  "group": "Thermocouples", "role": "Temperature above sample" }
```

`cartesian` → `a=x, b=y, c=z` [мм]; `cylindrical` → `a=r` [мм], `b=φ` [град], `c=z` [мм].

Геометрия задаётся на устройстве и может переопределяться на канале (термопарная
гребёнка: одно устройство, восемь разных `z`). Она нужна для будущих `T(z)`, `T(r)`,
`T(r,z)`, тепловых карт и пространственных распределений — виджеты `Heatmap` и
`XY Chart` (M6) читают именно её, поэтому формат зафиксирован уже сейчас.
