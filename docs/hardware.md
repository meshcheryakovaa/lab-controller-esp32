# Аппаратный слой: ChipProfile, ResourceManager, шины

## Реализация (Milestone 2)

```
buses/
├── II2cBus.h  IGpioPort.h  IAdcPort.h  IBusProvider.h   интерфейсы, без Arduino
├── I2cScanner.{h,cpp}                                   сканирование + подсказки
└── esp32/
    ├── WireI2cBus.{h,cpp}          поверх TwoWire, с таймаутом и учётом ошибок
    └── Esp32BusProvider.{h,cpp}    GPIO- и ADC-порты, настройка шин из system.json
```

Драйвер получает `IBusProvider*` в `DeviceContext`. Он не создаёт шину, не
настраивает её пины и не знает, какой это экземпляр периферии. Настройка шин —
отдельный интерфейс `IBusConfigurator`, доступный только `SystemManager`:
использовать шину и переконфигурировать её из-под соседей — разные права.

`system.json`:

```json
{ "schemaVersion": 1,
  "buses": { "i2c": [ { "index": 0, "sda": 21, "scl": 22, "frequency": 400000 } ] } }
```

Шины не пересоздаются при `reloadConfiguration()`: пины шины живут дольше
устройств на ней, а повторный `Wire.begin()` на работающем контроллере — хороший
способ его повесить. Смена пинов шины требует перезагрузки, и UI об этом говорит.

## ChipProfile — возможности кремния как данные

Карта пинов хранится таблицей, а не набором `#ifdef` по драйверам. Из этого следуют
три практические вещи: ResourceManager может назвать точную причину отказа, UI может
погасить невозможный пин, а тесты пиновой валидации гоняются на хосте.

```cpp
struct GpioCapability {
  bool exists, inputOnly, reserved, strapping, touchCapable;
  std::int8_t adc1Channel, adc2Channel;   // -1 = нет
  const char* note;                       // показывается пользователю дословно
};
```

Поддержка нового чипа = новая таблица в `core/ChipProfile.cpp`. Больше нигде.

### ESP32 (WROOM-32) — что важно знать

| Пины | Особенность | Как реагирует система |
|---|---|---|
| 6–11 | подключены к SPI-flash | `GPIO_RESERVED`, выбрать невозможно |
| 34–39 | только вход, без подтяжек | `GPIO_INPUT_ONLY` при попытке сделать выходом |
| 0, 2, 5, 12, 15 | strapping | разрешены, но с текстовым предупреждением в UI |
| 16, 17 | заняты PSRAM на WROVER | предупреждение |
| 1, 3 | UART0, консоль | предупреждение |
| ADC2 (0,2,4,12–15,25–27) | не работает при включённом Wi-Fi | `ADC_CHANNEL_INVALID` для аналогового входа |
| ADC1 (32–39) | работает всегда | разрешено |

Последняя строка — из тех, что экономят дни отладки: аналоговый вход на ADC2 не
«иногда врёт», он молча возвращает мусор при активном радио. Проще запретить.

## ResourceManager

Отслеживаемые ресурсы: `GPIO`, `ADC1`/`ADC2`-каналы, `I2C_BUS`, **`I2C_ADDRESS`
(адрес на конкретной шине)**, `SPI_BUS`, `UART_PORT`, `PWM_CHANNEL`, `PWM_TIMER`.

Два независимых вопроса:

```cpp
// 1. Способность: возможно ли это физически?
resources.checkPinCapability(34, PinUse::kDigitalOutput);
//   → GPIO_INPUT_ONLY, "this pin has no output driver"

// 2. Владение: свободно ли это сейчас?
resources.claimPin(21, PinUse::kDigitalInput, device, "HX711 #1 DOUT");
//   → RESOURCE_BUSY, "used by I2C0 SDA"
```

`releaseAllOwnedBy(device)` — единственный корректный способ отката. Драйвер захватил
DOUT, упал на SCK — `DeviceManager` откатывает всё одним вызовом. Классический баг
«пин занят после неудачного добавления устройства» структурно невозможен.

Адреса I²C: `0x38` на шине 0 и `0x38` на шине 1 — **разные** ресурсы. Два AHT20 с
одинаковым адресом на разных шинах — законная конфигурация, и система это понимает.

## Шинные менеджеры

### I²C

```json
{ "bus": 0, "sda": 21, "scl": 22, "frequency": 400000, "pullups": "external" }
```

Пины SDA/SCL захватываются как `PinUse::kBusSignal` от имени системы, поэтому любая
попытка отдать GPIO21 датчику даёт понятную ошибку.

Сканирование (`POST /api/v1/buses/i2c/0/scan`):

```json
{ "bus": 0, "sda": 21, "scl": 22, "frequency": 400000,
  "found": [
    { "address": "0x29", "claimed_by": null,
      "candidates": [ { "module": "vl53l0x", "confidence": "likely" } ] },
    { "address": "0x38", "claimed_by": "aht20_01",
      "candidates": [ { "module": "aht20", "confidence": "likely" } ] },
    { "address": "0x76", "claimed_by": null,
      "candidates": [ { "module": "bmp280", "confidence": "possible" },
                      { "module": "bme280", "confidence": "possible" } ] } ] }
```

**Догадка остаётся догадкой.** Адрес 0x76 носят и BMP280, и BME280, и несколько чужих
чипов. Поэтому `candidates` — это подсказка для формы, а не автоматический выбор.
Подтверждение приходит только от драйвера, прочитавшего chip ID в `begin()`.
Формулировки в UI: «probable AHT20», а не «AHT20 detected».

Ошибки шины считаются по устройствам (`NACK`, таймаут, арбитраж) и видны в
диагностике: одиночный NACK — норма, сто в минуту — плохой контакт.

Две детали реализации, о которых стоит знать:

* **`setTimeOut(25)` обязателен.** Без таймаута зависший ведомый, удерживающий
  SDA в нуле, вешает управляющую задачу навсегда, и watchdog перезагружает
  прибор посреди эксперимента.
* **Чтение регистра — это `writeRead` с повторным стартом**, а не отдельные
  write и read. Разделённые STOP'ом, они позволяют другому мастеру вклиниться, и
  чтение молча вернёт содержимое чужого регистра.

### SPI

Захватываются шина (`HSPI`/`VSPI`), пины MOSI/MISO/SCK, отдельно CS каждого
устройства. Тактовая частота и режим — параметры устройства, а не шины:
на одной шине могут жить АЦП на 20 МГц и SD-карта на 4 МГц.

### UART

`UART0` по умолчанию занят консолью и помечен как системный. Пользовательские
устройства получают `UART1`/`UART2`.

### GPIO / ADC

`GPIOManager` — тонкая обёртка над `pinMode`/`digitalRead`/`digitalWrite`,
существующая ради одного: проверить, что пин действительно захвачен вызывающим.
`ADCManager` применяет калибровку АЦП ESP32 (`esp_adc_cal`), поддерживает
усреднение по N выборкам и следит за аттенюацией.

### PWM (LEDC)

Каналы и таймеры — учитываемые ресурсы. У ESP32 16 каналов и 4 таймера; каналы,
делящие таймер, обязаны иметь одинаковую частоту. Менеджер группирует каналы по
частоте автоматически и отдаёт `PWM_CHANNEL_EXHAUSTED`, когда свободных нет —
вместо тихого переопределения частоты у уже работающего нагревателя.

## Модель параллелизма

| Исполнитель | Что делает | Приоритет FreeRTOS |
|---|---|---|
| `loopTask` (control) | `Scheduler::runPass()`: safety → control → acquisition → processing → telemetry | 1 (обычный) |
| HTTP/WS task (в составе `esp_http_server`) | REST, WebSocket, отдача файлов | 1 |
| Wi-Fi / LwIP | стек IDF | 18–23 |
| logger task (M10) | запись на SD/LittleFS, отдельно, чтобы I/O не тормозил сбор | 1 |

Почему не по задаче на модуль: каждая задача FreeRTOS стоит стек (2–4 КБ для всего,
что трогает `Wire` или ArduinoJson). Тридцать устройств съели бы всю кучу одними
стеками, а каждая общая структура потребовала бы мьютекса. Поэтому опрос,
обработка и регулирование выполняются кооперативно в одном планировщике, а драйверы
обязаны быть неблокирующими.

Данные между control-task и HTTP-task: снимок дескрипторов под коротким мьютексом;
значения каналов — атомарные `float` (32 бита, выровнены, чтение не рвётся).
Изменения конфигурации всегда выполняются в control-task через очередь команд.

Watchdog включён. `Scheduler` меряет длительность каждой задачи; задача, регулярно
превышающая свой период, видна на странице диагностики поимённо — вместе с
`max_duration_us`, `overruns` и `max_lateness_us`.
