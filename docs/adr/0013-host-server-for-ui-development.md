# ADR-0013. Веб-интерфейс разрабатывается против настоящей прошивки, а не против мока

**Статус:** принято (Milestone 4)

## Context

UI лабораторного прибора нельзя осмысленно разрабатывать вслепую: форму
добавления устройства надо видеть, ошибку валидации надо получить, сканирование
шины надо нажать. Плата при этом либо занята экспериментом, либо лежит в другой
комнате, либо ещё не собрана.

Стандартный ответ — написать mock-сервер на Node, отвечающий фиксированными
JSON'ами. Он даёт вторую реализацию API, которая расходится с настоящей на
второй неделе, и уверенность, которой не соответствует реальность.

## Decision

`tools/host_server.cpp` линкует **настоящие** `RestApi`, `DeviceManager`,
`ChannelManager`, `ConfigStorage`, `ProcessingManager` и настоящие драйверы и
отдаёт их по обычному сокету. Отличаются только транспорт (POSIX-сокет вместо
PsychicHttp) и файловая система (`PosixBackend` вместо LittleFS).

`platform/host/HostBusProvider` изображает плату, **к которой ничего не
подключено**: входы читаются как HIGH, I²C-сканирование не находит устройств,
АЦП сообщает, что заводской калибровки нет. Подделывать работающие датчики
здесь было бы вредно — для правдоподобных данных существуют модули-симуляторы.

WebSocket-телеметрия сознательно не реализована: рукопожатие и фрейминг — это
сотня строк транспорта, из которых нечего узнать. Дашборд получает начальные
значения из `GET /channels?values=1` и честно показывает связь как offline.

`tools/screenshot.mjs` прогоняет через Playwright сценарий приёмки этапа против
этого сервера.

## Alternatives

* **Mock-сервер на Node.** Быстрее написать, но это вторая реализация API.
  Расхождение с прошивкой — вопрос времени, а найдётся оно на живой плате.
* **Только `vite dev` против реальной платы.** Работает, когда плата есть и
  свободна; не работает в CI и не работает, пока железо не собрано.
* **Storybook с фикстурами.** Хорош для компонентов в изоляции, бесполезен для
  сценария «добавить датчик», который и есть смысл этого интерфейса.

## Consequences

**Плюсы.** Ошибка UI и ошибка прошивки различаются мгновенно: спорить не с кем,
API один. Валидация формы в браузере проходит через настоящий `ResourceManager`
и настоящие манифесты. Скриншоты в отчёте — это снимки работающей системы, а не
макеты. Весь интерфейс разрабатывается без платы (§59, распространённое на UI).

**Минусы.** Ещё одна цель сборки (`make -C tools host-server`). Нет телеметрии по
сокету, поэтому анимацию графика в этом режиме не посмотреть. Хост — это не
ESP32: он не покажет ни фрагментацию кучи, ни реальные тайминги шины;
`NullSystemMetrics` честно отдаёт нули вместо правдоподобных выдумок.

**Что это уже нашло.** При первом же прогоне UI против настоящей прошивки
всплыли три дефекта, которых не видел ни один unit-тест:

1. `?dry_run=1` одобрял HX711 на сборке без GPIO-порта, а создание потом
   падало. Расхождение валидации и создания подрывает саму идею живой проверки
   формы. Исправлено: модуль **декларирует** потребность (`BusRequirement::kGpio`
   / `kAdc` / `kI2c`), и `validate()` её проверяет.
2. **Драйвер, отказавший внутри `poll()`, оставался незамеченным.** Он менял
   своё внутреннее состояние на `ERROR`, а `DeviceRecord` продолжал говорить
   `RUNNING`: API отдавал здоровое устройство, дашборд показывал последнее
   значение как свежее. Добавлена сверка состояния после каждого опроса.
3. Карта GPIO загружалась один раз при старте, поэтому после добавления
   устройства селектор пинов предлагал уже занятые пины.

**Что нашёл повторный прогон этапа.** Второй проход по M4 против того же
сервера дал ещё четыре дефекта того же класса — «система молчит там, где должна
говорить»:

4. `?dry_run=1` **не проверял уникальность ключа**: форма показывала
   «✓ configuration is valid», а сохранение отвечало `409 ALREADY_EXISTS`.
   Ровно тот же разрыв между проверкой и созданием, что и в пункте 1.
   Проверка ключа перенесена выше ветки `dry_run`.
5. **Устройство, не поднявшееся при загрузке, исчезало без следа.** Его нет ни
   в `/devices`, ни в счётчиках `/system`, ни в диагностике: оно не существует
   как объект. `GET /system` теперь отдаёт блок `boot` с числом стартовавших и
   упавших устройств и с первым отказом поимённо, а SPA показывает баннер.
6. **Переход качества канала в `STALE` и `FAULTED` не доходил до браузера.**
   Телеметрия помечает канал «грязным» из обработчика нового отсчёта — а
   устареть и отказать канал может только тогда, когда отсчёты прекратились.
   Дашборд продолжал рисовать последнее число как свежее часами. `tick()` и
   `setSourceQuality()` теперь уведомляют слушателей о самом переходе.
7. График молча не рисовал третью величину: осей было две, а серия создавалась
   на несуществующей шкале. Теперь осей до трёх, а всё сверх того названо под
   графиком — линия без своей оси всё равно нечитаема.
