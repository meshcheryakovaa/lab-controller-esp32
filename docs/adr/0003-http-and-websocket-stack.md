# ADR-0003. PsychicHttp для HTTP и WebSocket, за адаптером

**Статус:** принято (Milestone 0), реализация в Milestone 3

## Context

Прошивка обслуживает: отдачу SPA из LittleFS, REST API, WebSocket-телеметрию и
загрузку OTA-образа. Приоритеты проекта — надёжность выше UX (§49); отказ веб-сервера
во время шестичасового эксперимента недопустим.

## Decision

`PsychicHttp` 2.x (обёртка над `esp_http_server` из ESP-IDF) как HTTP/WS-сервер.
Прикладной код обращается к нему через тонкий `api/HttpServerAdapter`, так что смена
реализации стоит один файл.

## Alternatives

* **ESPAsyncWebServer (форк ESP32Async).** Приятнее API, шире примеры. Но приносит
  собственный `AsyncTCP` со своей задачей и своим стеком; в сообществе за ним тянется
  длинная история падений при нехватке буферов и при большом числе одновременных
  соединений. Для лабораторного прибора это не тот риск, который стоит принимать
  ради удобства.
* **WebServer из ядра Arduino.** Синхронный: обработка запроса блокирует loop-таск,
  что несовместимо с планировщиком реального времени.
* **Собственный сервер на lwIP.** Полный контроль, слишком высокая цена.

## Consequences

**Плюсы.** Работает на проверенном IDF-компоненте; управляемый расход RAM; поддержка
чанкованной отдачи, что позволяет стримить большие JSON и CSV без сборки в памяти;
WebSocket в той же задаче, без второго TCP-стека.

**Минусы.** API менее «сахарное», меньше готовых примеров; фиксированный лимит
одновременных соединений задаётся при конфигурации сервера и требует расчёта.

**Смягчение.** Ограничение WS-клиентов (4 по умолчанию) сделано явным и видно в
диагностике; при переполнении клиент получает `RATE_LIMITED`, а не молчаливый отказ.
Кадры телеметрии отбрасываются, а не ставятся в очередь.
