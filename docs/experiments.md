# Управление, правила, безопасность, эксперименты

Реализация: Milestone 8 (control) и Milestone 9 (experiments). Форматы зафиксированы
в Milestone 0, потому что от них зависят REST API, хранилище и будущий визуальный
редактор — менять их потом дорого.

## Три уровня принятия решений

```
┌──────────────────────────────────────────────────────────────┐
│ 1. SafetyManager   — жёсткие пределы, приоритет kSafety,     │
│                      игнорирует бюджет тика, из UI не        │
│                      отключается без явного подтверждения    │
├──────────────────────────────────────────────────────────────┤
│ 2. ExperimentManager — сценарий эксперимента                 │
├──────────────────────────────────────────────────────────────┤
│ 3. RuleEngine + PID  — пользовательская автоматика           │
└──────────────────────────────────────────────────────────────┘
```

Верхний уровень всегда перекрывает нижние. Безопасность не может быть реализована
пользовательскими правилами (§30): правило можно случайно удалить, перепутать
единицы или сделать зависимым от канала, который стал `STALE`.

## Safety Manager

```json
{ "schemaVersion": 1, "limits": [
  { "id": "max_surface_temp", "channel": "t_surface", "max": 80,
    "on_trip": [ { "output": "heater_power", "value": 0 },
                 { "action": "stop_experiment" } ],
    "latching": true },
  { "id": "heater_sensor_alive", "channel": "t_surface",
    "require_quality": ["GOOD"], "max_age_s": 3,
    "on_trip": [ { "output": "heater_power", "value": 0 } ], "latching": true } ] }
```

Второе правило важнее первого. Отвалившаяся термопара даёт не «слишком высокую»
температуру, а отсутствие свежих данных — и нагреватель без такого интерлока
разгоняется вслепую. Поэтому `SafetyManager` реагирует и на значение, и на
`quality`/возраст отсчёта.

`latching: true` — сброс только вручную оператором, после того как он посмотрел,
что произошло.

Fail-safe состояние каждого выхода задаётся в его конфигурации и применяется также
при: переходе источника в `ERROR`, срабатывании watchdog, перезагрузке, потере
питания (аппаратно — подтяжкой на плате, это уже вне прошивки).

## PID

```json
{ "key": "heater_pid", "input": "t_surface", "output": "heater_power",
  "setpoint": 60.0, "kp": 12.0, "ki": 0.35, "kd": 45.0,
  "output_min": 0, "output_max": 100,
  "sample_interval_ms": 250, "direction": "direct",
  "anti_windup": "conditional_integration",
  "derivative_on_measurement": true,
  "input_quality_required": ["GOOD", "STALE"],
  "on_input_fault": { "output": 0 } }
```

Детали, которые обязаны быть в реализации:

* **производная по измерению**, а не по ошибке — иначе смена уставки даёт удар по выходу;
* **anti-windup** обязателен: при насыщении выхода интегратор не накапливается;
* **безударное переключение** ручной/авто: интеграл подгоняется под текущий выход;
* **фактический dt**: планировщик не идеален, интегрировать надо по реальному интервалу;
* **реакция на плохой вход**: при `FAULTED`/просроченном отсчёте PID уходит в
  заданное безопасное значение, а не продолжает регулировать по устаревшему числу.

PID не знает типа датчика и типа нагревателя (§28) — только имена каналов.

## Rule Engine

```json
{ "key": "fan_assist", "enabled": true,
  "when": { "all": [
    { "channel": "t_center", "op": ">=", "value": 60, "hysteresis": 2, "for_s": 5 },
    { "state": "experiment", "op": "==", "value": "RUNNING" } ] },
  "then": [ { "output": "fan_speed", "value": 40 } ],
  "else": [ { "output": "fan_speed", "value": 0 } ] }
```

Поддержано: `all`/`any`/`not`, операторы `> >= < <= == !=`, `hysteresis`,
`for_s` (условие должно держаться), `debounce_s`, `edge` (срабатывание по фронту).
Действия: запись выхода, включение/выключение устройства или контроллера, смена
уставки, старт/стоп логирования, отметка события, поднятие аварии, остановка эксперимента.

Гистерезис обязателен для всех пороговых правил: без него шум последнего разряда
щёлкает реле десять раз в секунду.

## Эксперимент

```json
{ "key": "evaporation_60c", "name": "Evaporation at 60 °C",
  "metadata": { "operator": "", "sample": "", "description": "", "notes": "" },
  "steps": [
    { "op": "SET",            "target": "heater_pid.setpoint", "value": 60 },
    { "op": "WAIT_UNTIL",     "channel": "t_surface", "op2": ">=", "value": 59,
      "timeout_s": 900, "on_timeout": "abort" },
    { "op": "MARK_EVENT",     "label": "steady state reached" },
    { "op": "START_LOGGING",  "channels": ["mass_01", "t_surface", "humidity_01"],
      "rate_hz": 20 },
    { "op": "RUN_FOR",        "duration_s": 1800 },
    { "op": "SET",            "target": "heater_power", "value": 0 },
    { "op": "STOP_LOGGING" },
    { "op": "STOP" } ] }
```

Типы шагов: `SET`, `WAIT`, `WAIT_UNTIL`, `RUN_FOR`, `START_LOGGING`, `STOP_LOGGING`,
`MARK_EVENT`, `ENABLE`, `DISABLE`, `IF`, `LOOP`, `STOP`.

**Реализовано в Milestone 9** (ADR-0018): `SET`, `WAIT`, `WAIT_UNTIL`, `RUN_FOR`,
`MARK_EVENT`, `ENABLE`, `DISABLE`, `STOP`. `START_LOGGING` / `STOP_LOGGING`
известны парсеру и **отвергаются** им до Milestone 10: сценарий, который молча
ничего не записал, обещает набор данных, которого нет. `IF` и `LOOP` не
реализованы — словарь закрыт, и расширять его придётся в трёх местах (движок,
парсер, редактор); это осознанная цена того, что четвёртого места, где можно
выполнить произвольный код, не существует.

`SET` адресует: `<канал>` (выход), `<цикл>.setpoint`, `<цикл>.manual`,
`<цикл>.mode`. Цель разрешается **при разборе и заново при старте** — сценарий,
проверенный неделю назад против цикла, которого больше нет, не запустится.

Состояние запуска публикуется как каналы `experiment_state` и `experiment_step`:
дашборд, правила и блокировки говорят на языке каналов, и ни одному из них не
нужно знать, что эксперименты существуют.

Принципы:

* сценарий — **данные**, а не код. Каждый шаг — объект с `op`; движок — простая
  машина состояний. Это то, что позволит в M9+ сделать визуальный редактор
  (§32) без переделки backend;
* у каждого ожидания есть `timeout_s` и явное `on_timeout` (`continue` / `abort`).
  Шаг `WAIT_UNTIL` без таймаута — это зависший эксперимент в три часа ночи;
* эксперимент не может обойти `SafetyManager`;
* состояние эксперимента (`IDLE`/`RUNNING`/`PAUSED`/`ABORTED`/`FINISHED`, номер шага,
  время) — доступно как источник для правил и как канал для дашборда;
* прерывание в любой момент переводит выходы в fail-safe и корректно закрывает лог.

## Метаданные и воспроизводимость

К каждому запуску сохраняется: имя эксперимента и его id, оператор, образец,
описание, время старта/окончания, активный профиль конфигурации, список активных
устройств, id использованных калибровок, `config_revision`, версия прошивки, заметки.
Всё это уходит в заголовок CSV (`docs/storage.md`) — так, чтобы через год можно было
ответить на вопрос «чем и в какой конфигурации это померено» (§48).

## Выходы и уровень безопасности (Milestone 7)

**Выход — это не значение, а значение, которого система уверена, что кто-то всё
ещё хочет** (ADR-0016). Уверенность пропадает — выход уходит в безопасное
состояние. Обеспечивает это `OutputManager`: одна задача планировщика с
приоритетом `kSafety`, а не соглашение между драйверами.

| Событие | Что происходит с выходом |
|---|---|
| загрузка | безопасное состояние, всегда; опции «восстановить последнее» нет |
| команда истекла (`hold_s`) | безопасное состояние; продлить истёкшую нельзя |
| устройство перестало работать | безопасное состояние, `DEVICE_FAULT` |
| аварийный стоп | всё в безопасное состояние, команды отвергаются |
| снятие стопа | разрешает команды; **ничего не включает обратно** |
| удаление устройства | увод в безопасное состояние до уничтожения драйвера |

Безопасное значение разрешается **один раз**, в `DeviceManager`, до создания
драйвера, и одно и то же число попадает и в `OutputManager`, и в драйвер через
`DeviceContext::channelSafeValues`. Два читателя одного значения — две
возможности разойтись в том, что считать безопасным.

Канал показывает **применённое**, а не заказанное: нагреватель с пределом 60 %,
которому скомандовали 100 %, сообщает 60. Ограничение, которого не видно, —
ограничение, о работе которого никто не знает.

| Модуль | Что добавляет сверх «пин включён/выключен» |
|---|---|
| `digital_out` | объявленный безопасный уровень, инверсия |
| `relay` | минимальный интервал переключения — ресурс контактов конечен |
| `pwm_out` | частота, безопасная скважность |
| `heater` | **предел мощности**, безопасное состояние жёстко 0 %, обязательный срок команды |
| `fan` | минимальные обороты (ниже них вентилятор стоит и делает вид, что работает), кик-старт |

Переход **в** безопасное состояние никогда не ограничивается по частоте: ресурс
контактов — это Reliability, отпускание выхода — Safety, и второе не может быть
отвергнуто первым (§49).

SafetyManager с пользовательскими границами, PID и правилами — Milestone 8. Он
строится поверх этого уровня и пользуется тем же `trip()`.

## Запуск и его запись (Milestone 9)

Метаданные запуска — свойство **запуска**, а не сценария: оператор и образец
спрашиваются при старте, и запуск без оператора отвергается (§48).

Запись пишется при любом исходе, живёт в `/data/runs.json`, не входит в экспорт
конфигурации и ограничена восемью последними. `state`, `reason` и `step_reached`
пишутся вместе: прерванный запуск не может читаться как законченный.

Если контроллер перезагрузился посреди запуска, при старте находится маркер
открытого запуска и дописывается запись **ABORTED / restarted**. Ничего не
возобновляется — контроллер не знает, сколько его не было.
