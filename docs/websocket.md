# Протокол WebSocket

**Статус: реализовано (Milestone 3).** `TelemetryBatcher` собирает кадры и
тестируется на фальшивом сокете; адаптер PsychicHttp только передаёт байты.

Единственная конечная точка: `ws://<host>/ws/live`.
Один сокет на вкладку. Каждый лишний клиент стоит прошивке TCP-блок и буфер отправки,
поэтому SPA мультиплексирует всё через одно соединение.

## Направление сервер → клиент

### `channels` — батч измерений

```json
{ "type": "channels",
  "t": 1786550398241,
  "epoch": 1786550398241,
  "data":    { "12": 60.13, "13": 32.421, "14": 41.7 },
  "quality": { "14": "STALE" } }
```

* `t` — монотонное время устройства, мс. Используется для осей графиков.
* `epoch` — настенное время, мс. **0**, если время не синхронизировано; UI обязан
  в этом случае показывать относительные метки, а не врать про дату.
* ключи в `data` — `ChannelHandle` в виде строки. Короче пользовательских ключей
  и, что важнее, не меняются, когда оператор переименовывает канал прямо во время
  эксперимента.
* `quality` присылается **только для изменившихся** каналов. В нормальном режиме
  этого поля нет вовсе.

Батчинг — по времени, не по отсчёту. При `dashboard_rate = 5 Гц` и 20 каналах это
5 кадров/с примерно по 300 байт вместо 1600 отдельных сообщений.

### `device` — смена состояния устройства

```json
{ "type": "device", "handle": 7, "key": "vl53l0x_01",
  "state": "ERROR", "code": "DEVICE_NOT_RESPONDING",
  "detail": "I2C device 0x29 not found" }
```

### `alarm`

```json
{ "type": "alarm", "id": "over_temp", "active": true, "severity": "critical",
  "code": "SAFETY_INTERLOCK", "message": "T_surface 82.4 °C > limit 80 °C",
  "t": 1786550398241 }
```

### `experiment`

```json
{ "type": "experiment", "state": "RUNNING", "key": "evaporation_60c",
  "step": 4, "step_count": 6, "step_name": "Run 30 min",
  "elapsed_s": 431, "remaining_s": 1369 }
```

### `system`

```json
{ "type": "system", "level": "WARNING", "code": "FILESYSTEM_FULL",
  "message": "LittleFS is 94 % full" }
```

### `hello` — первое сообщение после установления соединения

```json
{ "type": "hello", "firmware": "0.1.0-m0", "schema_version": 1,
  "config_revision": 42, "server_time": 1786550398241, "max_rate_hz": 20 }
```

`config_revision` инкрементируется при любом изменении конфигурации. Если SPA видит
значение, отличное от того, с которым он загружал дескрипторы, он перечитывает
`/api/v1/channels` — это заменяет собой дублирование конфигурации в сокет.

## Направление клиент → сервер

```json
{ "type": "subscribe",   "channels": [12, 13, 14] }
{ "type": "unsubscribe", "channels": [14] }
{ "type": "rate",        "hz": 10 }
{ "type": "ping" }
```

* подписка — **одно объединение по всем клиентам**, а не набор на клиента: одна
  вкладка браузера — обычный случай, а фильтрация на клиента означала бы отдельную
  сериализацию для каждого. Клиент игнорирует то, что не заказывал;
* без `subscribe` сервер не шлёт измерения вообще. Открытая вкладка «Система» не
  должна стоить прошивке ни байта телеметрии;
* `rate` ограничивается сверху `max_rate_hz` из `hello`;
* управляющих команд по сокету нет: запись выходов, старт эксперимента и любые
  изменения конфигурации идут через REST (код ответа, аутентификация, журнал).

## Поведение под нагрузкой

1. **Кадр отбрасывается, а не ставится в очередь.** Если предыдущая отправка ещё не
   завершилась, новый батч не копится: телеметрия реального времени, устаревший кадр
   бесполезен, а очередь съест кучу. Счётчик отброшенных кадров виден в диагностике.
2. **Лимит клиентов** — 4 одновременных WS-соединения (настраивается). Пятое получает
   `RATE_LIMITED` и закрывается с понятным сообщением, а не молча деградирует.
3. **Приоритет.** Задача батчера — `TaskPriority::kTelemetry`, ниже сбора данных и
   регулирования. При исчерпании бюджета тика первым тормозит именно она.
4. **Обрыв связи ничего не ломает.** Сбор данных, PID, правила и логирование живут в
   прошивке. Браузер — только окно. Закрытая крышка ноутбука не влияет на эксперимент.
5. **Реконнект** — на стороне клиента, с экспоненциальной задержкой 0.5 → 10 с;
   после восстановления клиент заново подписывается и сверяет `config_revision`.

## Бинарный кадр (Milestone 6)

Для графиков с историей JSON становится накладным. Планируется дополнительный
бинарный кадр:

```
uint8  frame_type = 0x01
uint8  channel_count
uint16 sample_count
uint64 t0_us
uint32 dt_us
[ uint16 handle ] × channel_count
[ float32 value ] × channel_count × sample_count
```

Это ~4 байта на отсчёт вместо ~14 в JSON. Формат добавляется как **новый тип кадра**,
JSON остаётся — старый SPA после OTA не ломается.
