# Хранение, версионирование и миграции

## Реализация (Milestone 1)

```
IStorageBackend            контракт файловых операций, атомарность — его часть
├── LittleFsBackend        плата
└── PosixBackend           хост: тесты «обрыв питания», «нет места», «битый файл»
ConfigStorage              секции, schemaVersion, миграции, revision
ConfigApplier              документ → живая установка; read-only проекция обратно
JsonConfigView             IConfigView поверх ArduinoJson — единственная точка стыка
```

**Документ — источник истины** (ADR-0010). Живые объекты — его проекция, а не
наоборот: `DeviceRecord` не хранит копию конфигурации драйвера, поэтому двум
копиям нечем разойтись. Правка устройства = read-modify-write над `devices.json`
(`ConfigApplier::upsertDevice` / `removeDevice`) и повторное применение.

## Три уровня

| Носитель | Что там лежит | Почему именно там |
|---|---|---|
| **NVS** | Wi-Fi SSID/пароль, hostname, hash пароля, режим сети, счётчик загрузок, флаг «безопасный режим» | переживает перепрошивку и форматирование LittleFS; нужен до монтирования ФС |
| **LittleFS** (раздел 640 КБ на 4 МБ) | SPA (`/www`), вся конфигурация (`/config`), системный журнал | wear-leveling и устойчивость к обрыву питания; OTA этот раздел не трогает |
| **SD-карта** (опционально) | длинные логи экспериментов, сырые данные, экспорт | flash ESP32 не рассчитан на непрерывную запись часами |

Система обязана полностью работать **без** SD-карты: логгер в этом случае пишет в
LittleFS с жёстким лимитом и ротацией, и предупреждает, что места мало.

### Имя раздела — `spiffs`

В `partitions_4mb.csv` раздел файловой системы называется **`spiffs`**, хотя на
нём LittleFS. Это не опечатка: `LittleFS.begin()` из Arduino-ESP32 по умолчанию
ищет раздел с меткой `spiffs`, и таблица, где написано `littlefs`, даёт плату,
которая форматирует себя при каждой загрузке и не отдаёт интерфейс — с
единственной строкой про неудачное монтирование в качестве улики. Milestone 12
заплатил за это вечером. Метка теперь передаётся и в `LittleFS.begin()` явно
(`LittleFsBackend::kPartitionLabel`), чтобы монтирование не зависело от того,
совпадает ли умолчание библиотеки с таблицей разделов.

### Первая загрузка

Пять секций, которые читает загрузка — `system`, `devices`, `processing`,
`calibrations`, `control` — создаются **пустыми и валидными** при первом старте
(`ConfigStorage::ensureDefaults`). Загрузчики всегда умели обходиться без файла,
так что дело не в них: без этого первая загрузка новой платы печатала пять строк
уровня ERROR про отсутствующие файлы, то есть описывала совершенно нормальное
состояние прибора, которого никто не настраивал, языком аварии. Побочная выгода
важнее косметики — после первой загрузки файловая система выглядит ровно так же,
как у настроенного прибора, поэтому экспорт, импорт, бэкап и сравнение работают
одинаково в обоих случаях.

Существующий файл не перезаписывается никогда; повторный вызов создаёт ноль
файлов, и на это есть тест.

## Раскладка LittleFS

```
/www/                       собранный SPA, файлы .gz
/config/system.json
/config/devices.json
/config/channels.json
/config/processing.json
/config/calibrations.json
/config/virtual.json
/config/control.json         блокировки, PID-циклы и правила (M8)
/config/dashboards/*.json
/config/experiments/*.json
/config/profiles/*.json
/logs/                      системный журнал (кольцевой, 2 файла по 32 КБ)
/data/                      логи экспериментов, если нет SD
```

**Почему не один `config.json`.** Сдвиг виджета на дашборде переписывал бы файл, в
котором лежат калибровки. Это и износ flash (R4), и риск потерять калибровку при
обрыве питания во время сохранения дашборда. Разделение по времени жизни и частоте
записи — не вкусовщина.

## Атомарная запись

```
1. записать в /config/devices.json.tmp
2. закрыть файл (flush)
3. rename(devices.json.tmp → devices.json)   ← атомарно в LittleFS
```

При старте любой найденный `*.tmp` удаляется: значит, прошлая запись не завершилась,
и валиден именно старый файл. Прерванное сохранение никогда не оставляет систему
с полуфайлом.

## Версионирование

Каждый файл начинается с `schemaVersion`:

```json
{ "schemaVersion": 1, "devices": [ … ] }
```

Правила:

* **Версия выше известной → `CONFIG_SCHEMA_TOO_NEW`, файл не читается.**
  Прошивка не пытается угадать формат из будущего. Это штатная ситуация при откате
  OTA, и молчаливая порча конфигурации здесь была бы худшим исходом.
* **Версия ниже → миграция** цепочкой `v1→v2→v3`, каждая функция знает только соседний шаг.
* Перед миграцией оригинал копируется в `/config/backup/<name>.v<N>.json`.
  Если миграция упала — возвращаемся к копии и поднимаемся в безопасном режиме.
* Совместимые изменения (новое необязательное поле со значением по умолчанию из
  манифеста) версию **не** повышают.

```cpp
// storage/ConfigStorage.cpp — таблица есть уже в M1, пустая на schemaVersion 1
using MigrationFn = Status (*)(JsonDocument& document);
struct Migration { ConfigSection section; std::uint16_t from; MigrationFn apply; };

// Как будет выглядеть первая реальная запись:
// { ConfigSection::kDevices, 1, [](JsonDocument& d) -> Status {
//     for (JsonObject device : d["devices"].as<JsonArray>()) {
//       device["sample_interval_us"] = 1000000 / (device["rate_hz"] | 10);
//       device.remove("rate_hz");
//     }
//     return ok(); } },
```

Миграции применяются цепочкой `v1→v2→v3`, поэтому плата, отставшая на три
версии прошивки, обновляется корректно. Механизм существует с M1 намеренно:
первая настоящая миграция должна стоить две строки, а не редизайн.

У модулей есть собственный `ModuleManifest::schemaVersion`: если изменился смысл
параметра конкретного драйвера, мигрируется только его секция `config`.

## Порядок загрузки и безопасный режим

```
NVS → счётчик неудачных загрузок
  └─ >3 подряд → SAFE MODE: только Wi-Fi + API + страница диагностики,
                 устройства не поднимаются, конфигурация доступна на правку
LittleFS смонтирован? ── нет ──► формат + дефолтная конфигурация + предупреждение
  │
  ├─ system.json      (если повреждён → дефолт, событие CONFIG_CORRUPT)
  ├─ devices.json     (устройство с ошибкой → ERROR, остальные стартуют)
  ├─ channels/processing/calibrations/virtual
  ├─ control.json + safety
  ├─ сеть (STA → при неудаче AP)
  ├─ REST + WebSocket
  └─ dashboards/experiments по требованию
```

Одно битое устройство не мешает подняться остальным. Единственное, что останавливает
загрузку целиком, — недоступный `safety`: без интерлоков нагреватель не включается.

## Экспорт и импорт

`GET /api/v1/config/export` отдаёт один документ:

```json
{ "schemaVersion": 1, "exported": "2026-08-12T09:00:00Z",
  "firmware": "0.4.2", "chip": "esp32", "device_id": "a4:cf:12:…",
  "sections": { "system": {…}, "devices": {…}, "channels": {…},
                "processing": {…}, "calibrations": {…}, "virtual": {…},
                "control": {…}, "dashboards": {…}, "experiments": {…} } }
```

Импорт: проверка `schemaVersion` → миграция при необходимости → валидация **всех**
устройств против манифестов и `ChipProfile` целевой платы → и только потом запись.
Импорт конфигурации, снятой с ESP32-S3, на классический ESP32 отклоняется с перечнем
конкретных проблемных пинов, а не с общим «ошибка».

Секреты (пароль Wi-Fi, hash пароля пользователя) в экспорт **не попадают**.

## Данные экспериментов

CSV — основной формат (§33):

```
# experiment: evaporation_60c
# started: 2026-08-12T09:14:33Z (epoch_valid=true)
# operator: A. Mescheryakov
# sample: PDMS 20x20 mm
# config_revision: 42
# calibrations: mass_01=cal_7, t_center=cal_3
# columns: t_ms, epoch_ms, mass_01.raw, mass_01.g, t_center.degC, quality_mask
0,1786550398241,453210,0.001,59.98,0
50,1786550398291,453208,0.002,60.01,0
```

* обе метки времени в каждой строке — монотонная и настенная;
* `raw` пишется рядом с обработанным значением, если включено (§48) — тогда
  эксперимент можно пересчитать после уточнения калибровки;
* `quality_mask` — битовая маска флагов качества по колонкам;
* заголовок содержит `config_revision` и id использованных калибровок,
  то есть полное описание того, «чем это померено».

Ротация: новый файл каждые 16 МБ или каждый запуск эксперимента. При заполнении
носителя логгер останавливается и поднимает `FILESYSTEM_FULL` — он **не** удаляет
чужие данные самовольно.

**Реализовано в Milestone 10** (ADR-0019): `/data/logs/<id>.csv` плюс индекс
`/data/logs.json`. Заполнение носителя останавливает запись, а не установку;
набор данных помечается усечённым в футере, в индексе и в записи запуска.
Резерв 64 КБ отсчёты не пересекают: прибор обязан остаться настраиваемым.
Сессия, которая по арифметике не поместится, не начинается. В заголовке —
`config_fingerprint` (FNV-1a по всем секциям конфигурации), потому что счётчик
ревизий обнуляется при каждой загрузке и ничего не идентифицирует.
