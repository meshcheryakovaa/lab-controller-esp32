# Universal ESP32 Laboratory Controller

Универсальная модульная лабораторная платформа на ESP32 с веб-интерфейсом.

Прошивка содержит **универсальное ядро и библиотеку поддерживаемых модулей**.
Конкретная лабораторная установка собирается пользователем в браузере: датчики,
пины, калибровки, обработка, виртуальные каналы, дашборды, регулирование, сценарии
экспериментов и запись данных — **без изменения исходного кода и без перепрошивки**.

> Пользователь не программирует ESP32. Он собирает лабораторную установку.

Установка целиком описывается конфигурационным файлом: устройство появляется и
исчезает вместе со строкой в `devices.json`, и в `main.cpp` нет ни одного
упоминания конкретного датчика или GPIO.

Тензодатчик калибруется по трём гирям прямо в браузере, и канал начинает читать
граммы: единица, точность и диапазон переезжают вместе с числом, а прежняя версия
остаётся на месте — откат к ней стоит одного нажатия.

Дашборд собирается мышью: плитки перетаскиваются по сетке в 12 колонок,
раскладка пишется на плату через две секунды после последнего движения и
переживает перезагрузку. Прошивка при этом не знает, что такое «виджет» —
она проверяет форму, границы и ссылки на каналы, а словарь виджетов живёт в
интерфейсе (ADR-0015).

Установка не только измеряется, но и управляется — и **выход никогда не остаётся
включённым сам по себе**: он поднимается в безопасном состоянии, отпускает его,
если команду перестали продлевать, и уходит туда же, когда устройство отказало
или поднят аварийный стоп (ADR-0016).

Установкой можно управлять автоматически — и **ни один уровень не доверяет
соседнему** (ADR-0017). Регулятор решает и командует; `SafetyManager` смотрит на
**каналы**, а не на регулятор, и может остановить всё; срок годности команды
отпускает выход зависшего регулятора. Цикл, потерявший датчик, отпускает выход и
говорит, почему; блокировка со STALE-входом срабатывает, а не даёт презумпцию
исправности; аварийный стоп нельзя снять, пока защёлкнута хоть одна блокировка.

Уставка переживает перезагрузку, право регулировать — нет: любой цикл
поднимается в `off`.

Установка выполняет **сценарии** — и сценарий это данные, а не код (ADR-0018).
Каждый шаг — объект с `op` из закрытого словаря; редактор в браузере генерируется
из того же словаря и не содержит ни одного поля, которое прошивка бы вычисляла.
У каждого ожидания обязателен таймаут, эксперимент никогда не главнее блокировок,
после перезагрузки ничего не возобновляется, а **прерванный запуск невозможно
спутать с законченным**: запись несёт исход, причину и номер шага, на котором всё
остановилось, вместе с оператором, образцом, версией прошивки и id калибровок.

Эксперимент **записывает себя**: CSV с заголовком, который через год отвечает на
вопрос «чем и в какой конфигурации это померено» — оператор, образец, прошивка,
отпечаток конфигурации, id активных калибровок, обе метки времени в каждой
строке, сырое значение рядом с обработанным и маска качества.

Когда носитель кончается, останавливается **запись, а не установка** (ADR-0019):
полная карта — это проблема воспроизводимости, а не безопасности, и убивать
восьмичасовой образец из-за неё нельзя. Набор данных при этом помечается
усечённым в трёх местах сразу, 64 КБ резерва отсчёты не трогают никогда, а
сессия, которая по арифметике не поместится, просто не начинается — с обоими
числами в сообщении.

Прибор можно запереть, **ни разу не заперев кнопку остановки** (ADR-0020).
Пароль защищает от случайности и от постороннего в той же сети — и не
претендует на защиту от того, кто стоит рядом с кнопкой питания. Аварийный стоп,
остановка запуска и освобождение выхода работают без входа; **снятие** стопа —
нет. Действия, которые убирают защиту (удаление блокировки, импорт
конфигурации, OTA, смена пароля), требуют пароля **в самом запросе**, что бы ни
говорила сессия. OTA вдобавок отвергается, пока стенд что-то делает.

Хеш пароля физически не может попасть в экспорт: учётные данные — не секция
конфигурации. PBKDF2-HMAC-SHA256 написан целиком и проверен опубликованными
векторами на хосте, потому что проверка пароля, существующая только на плате, —
это проверка, которую никто никогда не проверял.

И, наконец, прошивка **собирается для платы** — что до M12 было предположением
(ADR-0021). Шесть файлов с Arduino внутри не компилировал никто, и первая же
сборка нашла в них незакрытый `namespace`, четыре обращения к изменившемуся API
веб-сервера, удалённую константу ArduinoJson и переполнение DRAM на 10.6 КБ.
Теперь эти файлы собираются на хосте при каждом прогоне — **против настоящих
PsychicHttp 2.2.0 и ArduinoJson 7.4.3**, чьи версии зафиксированы, а не заданы
диапазоном. Бюджет статической памяти стал падающим тестом, а не сообщением
линкера; маршруты веб-сервера явные и одинаковые на плате и на сервере
разработки; а сборка не может молча отгрузить пустой интерфейс.

## Быстрый старт

```bash
git clone <repo> && cd lab-controller

# тесты ядра — плата не нужна
cd firmware && pio test -e native
#   или без PlatformIO, одним компилятором:
tools/run_tests.sh            # шесть наборов
SAN=1 tools/run_tests.sh      # они же под ASan + UBSan

# шесть ESP32-файлов: собираются ли они и согласны ли с библиотеками
tools/esp32_typecheck/check.sh

# прошивка (интерфейс собирается автоматически; см. tools/build_frontend.py)
pio run -e esp32dev -t upload
pio run -e esp32dev -t uploadfs    # без этого плата отдаёт «интерфейс не установлен»
pio device monitor

# жива ли плата, до и независимо от интерфейса
curl -v http://192.168.4.1/health
```

После прошивки плата монтирует LittleFS, поднимает шины и устройства из
`/config`, и печатает отчёт о загрузке в консоль: сколько шин стартовало,
сколько устройств поднялось, что именно не получилось и в каком поле.

## Архитектура в одном экране

```
Physical Hardware → Driver(IDevice) → Device → Raw Channel
                  → Processing (calibration → filters → compensation)
                  → Channel → Control / Logging / Formula → Dashboard
```

Каждый уровень независим. Дашборд никогда не обращается к датчику — только к каналу.

```
firmware/src/
├── core/        ядро без Arduino: реестр, ресурсы, планировщик, шина событий
├── platform/    esp32/ и host/ — реализации HAL
├── buses/       интерфейсы I2C/GPIO/ADC + реализации ESP32 + сканер шины
├── modules/     sensors · outputs · processing · control · virtual
├── services/    каналы, устройства, обработка, калибровка, правила, эксперименты
├── storage/     backend (LittleFS / POSIX), ConfigStorage, ConfigApplier
├── app/         SystemManager: порядок старта, safe mode, главный цикл
└── api/         REST + WebSocket
```

Пример: чтобы установка появилась, достаточно двух файлов в `/config`.

`system.json` — какие шины поднять:

```json
{ "schemaVersion": 1,
  "buses": { "i2c": [ { "index": 0, "sda": 21, "scl": 22, "frequency": 400000 } ] } }
```

`devices.json` — что на них висит:

```json
{ "schemaVersion": 1,
  "devices": [
    { "key": "balance_01", "module": "hx711", "name": "Sample balance",
      "sample_interval_us": 100000,
      "config": { "data_pin": 16, "clock_pin": 17, "gain": 128, "rate_hz": 10 },
      "channels": { "mass": { "key": "mass_01" } } },

    { "key": "air_01", "module": "aht20", "name": "Chamber air",
      "config": { "bus": 0, "address": "0x38" },
      "geometry": { "system": "cylindrical", "a": 25, "b": 0, "c": 10,
                    "group": "Chamber", "role": "Air above sample" } },

    { "key": "baro_01", "module": "bmp280", "name": "Barometer",
      "config": { "bus": 0, "address": "0x76", "oversampling_p": 16 } } ] }
```

Прошивка при этом не пересобирается. Ошибка в конфигурации не роняет остальные
устройства: отчёт назовёт ключ устройства, поле и причину.

## Критерий качества проекта

Чтобы подключить новый поддерживаемый датчик, пользователь:
подключает его физически → открывает браузер → **Add Device** → выбирает тип →
задаёт интерфейс и пины → калибрует → добавляет канал на дашборд.

Прошивка при этом не меняется.
